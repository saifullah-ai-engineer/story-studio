# Maintenance Workflow

New content enters from a directory or files provided by the user, and the original files stay unchanged. Normal topic selection and drafting do not modify the skill library. A published copy only saves the snapshot path and content hash inside the library, without keeping the original computer directory, original file name, or personal collection time; the mapping for private sources sits outside the skill directory.

1. Use `scan` to compare read-only what is new, what changed in content, and which originals are not found in the current directory. The comparison is based on SHA256; a missing item is only a check result and does not trigger deletion. A changed old draft is saved as a new version, without overwriting the old snapshot.
2. Read the full text of what is new, and confirm the body is complete, along with the account, platform, video ID, metrics, and collection date. When there is no publication date, keep the value empty. The same video ID, the same body text, a renamed duplicate, and the same story told differently are handled separately; only drafts that meet the user's selection criteria enter the formal highly liked library.
3. Assign each piece the next unused H number, save the byte-identical `corpus/raw/Hxxx.md` and the original SHA256. Save the cleaning result separately in `clean/`, recording each change item by item; do not automatically correct uncertain personal names. Follow the complete field set of the existing `meta/Hxxx.json`, and manually add era, people, conflict, template, structure, story cluster, source nature, risk, and new angles. `fact_status` defaults to not fully verified.
4. Use the structured JSON API to merge `catalog.json`, making sure each entry matches its corresponding meta file. Update the readable topic library. When a new theme has only one or two pieces, first label it as a trial, and do not rashly turn it into a global rule.
5. Recalculate the affected distributions; `statistics.json` is a snapshot of the first 57 pieces, and until it is recalculated its version note must keep it labeled as an old snapshot, so it is not passed off as updated statistics. The statistics method is in the language document; new style rules need evidence across pieces, and material not used in the induction must be chosen for rechecking.
6. The opening special topic is updated along with the corpus: add the main and secondary types, the original tension cue and the end of the unit, the first sentence's task, the advance, the promise, and the risk to `corpus/hook_annotations.tsv` piece by piece; semantic judgment cannot be replaced by automatic keyword matching. In the private repository, run `python -X utf8 tools/build_hooks.py` to rebuild the JSON and the per-piece analysis; that repository's maintenance tool is not installed with the user copy. Revise the statistics, boundaries, and evidence in the opening guide in step, and do not present new samples as already verified.
7. Run `validate`; check the original hashes and paths, then do one trial write on a new topic and a word-count check. An opening update needs a test of how multiple versions of the same topic differ, whether the facts are consistent, where to stop when only hooks are wanted, and short-duration counting. First complete and verify in a copy, then update the installed version; do not modify the rules in the background during drafting.

8. This directory is story-studio's built-in working copy; here, only built-in resources the user explicitly asks to maintain are updated and checked, and other installation directories are not automatically published to or modified.

Full semantic distillation is done by the assistant reading this skill; `scan` is only responsible for reliably identifying file changes, and does not claim to complete understanding of a new draft automatically. The record of topics already used in the user's projects is maintained separately, and "generated" cannot be treated as "published".
